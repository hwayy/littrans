# Continue Literature Translation

Use [host-runtimes.md](../../references/host-runtimes.md) for local execution and [fidelity-workflow.md](../../references/fidelity-workflow.md) for state and recovery.

You coordinate and never do a stage's work in your own context. Dispatch every translate, revise, transcribe, audit-lens and asset-audit packet to a fresh subagent of the stage's agent (table in host-runtimes.md), with the packet's model (and effort on Codex). When status returns `source-review`, repair the pages as step 4 of `prepare-literature-source` does. Only if the host offers no subagents, run each stage in a separate fresh session and tell the user.

1. When the user asks to translate verified pages that no batch covers yet, cut them first with `batch create PROJECT --pages PAGES`, which cuts at logical boundaries and keeps paragraphs, theorems and derivations whole; never cut batches for pages the user has not asked to translate. Recover the requested resume boundary from the durable checkpoint. Select a bounded wave with `workflow next PROJECT --start-at ID`, adding `--through ID` for a fixed endpoint. An unbounded selection is valid for a new project. Do not restart historic unfinished batches outside the user's scope.
2. Keep the selected batch IDs fixed and use `workflow status PROJECT --batch-ids IDS` for their separate dependencies. Codex and Claude Code waves default to 3 batches (Claude Code maximum 6); Cursor defaults to 6, maximum 9. Wave size is not the simultaneous child-task count: obey actual host capacity. A batch set for a packet or a render may mix batch series (for example `p0010-p0013-b001,p0021-p0023-b001`) as long as units do not overlap and source order is kept; within one series the batches must stay consecutive.
3. For each fidelity-ready batch, create a `--stage translate` packet and dispatch a fresh `literature-translator` subagent. Formula transcription is optional enhancement: schedule `--stage transcribe` (a fresh `literature-transcriber`) only when requested or selected, at any later time including after final rendering. Parallel execution is optional; both workers see original English and images, neither sees the other's candidate. Dispatch each with the model and effort in its packet, resolved from that stage's own role in the project's `agent_models.<host>` (on Claude Code the agent's `effort: high` frontmatter applies instead of a packet effort); a packet that records neither dispatches on the host's default, which the CLI reports as an advisory rather than refusing. Report a configured model that is unavailable rather than substituting. Target about 900 source words and a soft limit of 60 assets, cutting at logical boundaries rather than inside a derivation or a theorem with enumerated parts and displays. Preserve reviewed `parent_id` groups as complete units of scope.
4. Submit translation and any optional transcription separately. Finish `context/document-brief.md`, `context/style-guide.md` and `glossary/approved.yaml` before the audit wave: the three-lens coverage is bound to the two context files whole, so a later edit resets it for every audited batch, and to the approved and reference entries per unit, so a glossary edit resets only the batches that mention the entry (append chapter-specific names and senses to `glossary/reference.yaml`, never to the context files) (`workflow status` and `review status` report the reason under `audit_stale` / `audit_stale_reasons`, e.g. `context-changed`, `dependency-changed`, `unit-changed`, `invalidated`). Once a translation passes QA, issue `--stage audit --lens all` packets immediately and dispatch each lens packet to a fresh subagent of its lens reviewer, in consecutive groups of at most three batches. For submitted asset candidates, separately issue `--stage asset-audit` to a fresh `literature-asset-reviewer`, distinct from the transcriber, with original images and candidate render evidence.
5. Import all reviews, including empty translation-lens results; `review import-set` rewrites reviewer ids to canonical `audit-<hash>` ids and keeps the reviewer id as `source_issue_id`, and either resolves. When status reports `revise`, create a `--stage revise` packet: it carries the current translation records, the open issues and `<batch>.revise.md`, so a fresh `literature-translator` subagent consolidates every open issue into one resubmission, runs QA and reports the addressed issue ids. Close them with `review resolve PROJECT BATCH id1,id2 --resolution "..."` (`review issues PROJECT BATCH` lists what is still open), then run the missing closure checks returned by status. Keep uncertain assets as original images. For a rejected candidate, create a new `assets packet --asset-ids IDS --revision-notes "specific feedback"` and dispatch a fresh transcriber plus an independent asset re-audit; reuse the original cached response only as history. Do not wait for LaTeX completion to audit an otherwise understandable translation.
6. Machine-approve only with current source fidelity, passing QA, all three translation lenses and resolved blocker/major issues. Preserve configured external reviewer models, service concurrency and required second opinions. Follow the audit skill's external-review reference.
7. Render each batch independently after its configured gate and cross-batch dependencies pass. A project with no transcription candidate renders originals-only automatically (`originals_only_reason` in the render QA); the edition header and `*.quality.md` reflect the rendered batches, not the project-wide high-water mark. Check the original-image fallback and asset status separately from translation status. Persist the next in-scope resume boundary and the outstanding asset queue; rendering a translation does not mean transcription is complete.

Cache successful outputs immediately, import idempotently and repair serialization offline before retrying model calls. Record unknown usage as unknown. Do not reuse stale packet bindings or a reviewer's self-reported model as host evidence.
